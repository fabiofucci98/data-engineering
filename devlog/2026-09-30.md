## 14. "Can pgAdmin auto-find the databases?" `info gathering`

**Core idea:** the human asked whether pgAdmin could automatically discover/register the
two stack databases instead of registering servers manually each time.

**Done:** agent answered (no code changed): pgAdmin has no network auto-discovery, but
you can pre-seed its server registry (`servers.json`, the same file pgAdmin writes on
manual registration) plus a `pgpass` password file, and mount both into the container
(bind-mounted into `/var/lib/pgadmin/storage/<login-email-folder>/servers.json`, with
`PGPASSFILE` set). Verified the approach against the official pgAdmin container docs
(even document an "import-servers-json" init-container pattern). Concrete recipe for this
repo: a `pgadmin/servers.json` + `pgadmin/pgpass`, root compose mounts + `PGPASSFILE`,
one-time `docker compose down -v` of the root stack so the seeded file takes effect on
existing volumes. Caveats flagged: no real discovery (host changes need file changes),
keyed to the login email, one-time pgAdmin state reset. Implementation offered but not
done yet — the human decides.
**Who:** human asked; agent researched (official docs) and answered.
**Status:** 🟢 (answered — implementation pending the human's go/no-go)

## 15. pgAdmin auto-registration — implemented + corrected `change request`

**Core idea:** the human said **go** on auto-registering the two databases in pgAdmin.

**Done (with a correction to block 14):** the first attempt followed the legacy
*storage-dir* recipe (mount `servers.json` into `/var/lib/pgadmin/storage/<user>/`).
It failed hard: Docker creates those mount parent dirs as root, and pgAdmin 500s with
"user does not have permission to read and write to the specified storage directory"
(container runs as uid 5050/gid 0). Grepping the image's `/entrypoint.sh` revealed the
**official mechanism**: the entrypoint auto-runs `setup.py load-servers <file> --user
<email>` at first init when `PGADMIN_SERVER_JSON_FILE` exists (default
`/pgadmin4/servers.json`). The fix is therefore trivial and robust: mount
`pgadmin/servers.json` to `/pgadmin4/servers.json` in the root compose (env
`PGADMIN_SERVER_JSON_FILE` documents it) — no custom entrypoint at all. Verified: on a
fresh pgAdmin volume the boot log prints "Added 0 Server Group(s) and 2 Server(s).", the
config DB shows both servers (`sci-db`, `city-db`, user postgres), and a container on
`sdp-shared` connects to both DBs. (Also learned: compose interpolates `$VAR` inside
`entrypoint:` scripts — use `$$` — and pgAdmin's native "auto-discovery" only scans
local/registry Postgres, not LAN hosts, so file seeding is the correct route here.)
**Blocker flagged:** at some point both DB stacks had been cleanly stopped (`Exited (0)`,
coinciding with a gap in the session); the agent restarted both — data intact, verified
healthy, counts unchanged. Cause unknown (likely a manual stop or Docker Desktop state);
worth watching.
**Who:** human ordered the feature; agent implemented, debugged, corrected course,
verified, and restarted the stacks.
**Status:** 🟢 (implemented & verified — pending human review/commit)
